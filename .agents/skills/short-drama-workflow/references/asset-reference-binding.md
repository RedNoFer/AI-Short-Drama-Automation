# 资产引用绑定规范（唯一真值）

**固定资产代码属于制作包，上传槽位编号由应用提交时生成。** Wan/Seedance离线包保留 `CHAR_01/LOC_01/PROP_01`，不预写 `@ImageN/@图片N`；H3素材标签按其分支规范映射，不能把资产代码中的数字误判为图片编号。

这份文件管「提示词里的资产怎么被指到正确的图上」，人物、场景、道具一视同仁。导入格式见[精简制作包导入规范](compact-import.md)，资产图本身怎么出见[资产图制作规范](asset-image-production.md)，**资产图与视频提示词各自写什么、不重复什么见[提示词分层规范](prompt-layering.md)**。

## 一、为什么"已经抽离成参考块"仍然全错

2026-10-23 连续在两部片上复现：`三千国道逆己而行-Wan3.0`（5 角色）与 `替身千金`（娜琳／塔纳／护士等）。表现一致——角色拿到别人的脸、场景图被当成人物、道具完全没被引用。

三层原因，缺一层都不会出事，三层叠加就成了系统性错位：

1. **编号是应用的，不是包的。** 应用在提交时按本次上传的图片槽位生成一份**全局**清单：`@图片1：… @图片2：…`。包里的每个片段却各自从 1 开始编号（`@Image1=CHAR_01`），等于每个片段都自造一套序号。两套序号之间没有任何同步机制。
2. **应用清单的顺序不由包决定。** 它可能随上传顺序、拖拽顺序、类型分组变化；同一次提交里，预览框的顺序和实际出片卡上的 `【参考图片】` 顺序都可能不同。包内写死的数字无法预测它。
3. **"抽离"只搬了位置，没有取消数字。** 把散落在正文里的 `@ImageN` 收进一个 `【参考】` 块，确实让改起来更集中，但**写死编号这件事本身没变**。只要包里还有数字，就永远存在"包说一套、应用排一套"的可能。

**结论：Wan/Seedance离线包不预写上传槽位号，保留固定资产代码与引用职责。**

## 二、引用规则

| 编号 | 规则 | 机检 |
|---|---|---|
| **R1** | Wan/Seedance离线包不预写 `@ImageN/@图片N/图N` 上传槽位号；H3使用本分支 `<Subject N>` 等标签，`<Picture N>` 仅指实际上传且已登记的图 | 按登记分支校验，不跨轨套用 |
| **R2** | 固定资产标题按导入格式定义代码与名称；片段绑定行写代码；Wan/Seedance `【参考】` 写 `代码＝职责`；视频动作正文用姓名或资产名；H3按本分支标签引用 | 绑定代码必须与固定资产区一致，不重复拼接代码与名称 |
| **R3** | 默认资产形态：Wan角色＝单人塑像图，Seedance/H3角色＝四视图；用户已选参考图版式优先，内部登记覆盖；场景＝空镜全景图（0人0车），道具＝基础态单张 | `WAN30-01/04`；SCENE-01/02 |
| **R4** | 参考职责必须是**正向**的：`＝身份与服装唯一基准`。禁止写「只作身份比对」「不作视频参考帧」——写了就等于主动放弃图锚 | `WAN30-05` |
| **R5** | 服装变体必须与默认装**真正不同**；写「与默认装同款」等于同一套衣服登记两次 | 机检「同款」判错 |
| **R6** | 每个角色有明确身份图锚；可写`姓名：身份外观遵循 CHAR_xx 人物参考图`，同码须已绑定且有参考职责；需要三锚时只写同源识别项，不复述服装细节 | `WAN30-06` |
| **R7** | 从正文实际出镜者及具名发声者反查绑定与参考，再核公共名单/声线及服装持物；阶段 4 全套提示词评审核对见[角色引用闭环验收](character-reference-closure.md) | `CAST-01～04`＋语义评审 |

Wan/Seedance上传槽位编号在应用提交时生成；H3标签遵循其已登记素材映射。下面的四段示例适用于Wan/Seedance，H3仍使用自己的固定字段结构。

## 三、标准写法

```text
【参考】
CHAR_01＝身份与服装唯一基准（单人塑像图，全片不变）
CHAR_02＝身份与服装唯一基准（单人塑像图，全片不变）
LOC_01＝空间拓扑与光位基准（全景）
PROP_01＝形制基准（基础态单张）
```

- 一行一个资产，`代码＝职责`，中文分号或换行分隔，句号收尾。**代码后不要再写名称**：应用会把 `CHAR_01` 解析成角色名，写成 `CHAR_01 娜琳＝…` 会渲染成「娜琳 娜琳＝…」，既重复又可能被模型读成两个人。
- 职责只写**这张图负责什么**（身份／服装／空间／光位／形制），不写编号、不写上传位置。
- 没被本片段用的资产不写进来；正文不会因上传清单多出资产就新增角色。提交前仍须按绑定清单移除无关参考，不能假定多余图片不会影响生成。

### 人物正文

```text
【公共总规范】…阿泽：黑色碎短发／左手腕旧手绳／深灰机能外套。苏晚：齐肩黑发／细框银边眼镜／雾蓝外套。…
```

只写**三个识别锚**：发型 ／ 固定饰件 ／ **外套品类＋固有色**（如「藏青夹克」「白色大褂」「米色连衣裙」）。剪裁、版型、面料、领口袖口、拉链纽扣、内搭、裤、鞋全部交给参考图，正文重复一遍就是给模型第二个真值。状态变化用「在参考图服装基础上…」（淋湿、沾泥、拉起帽子、解开前襟）；换整套衣服另立服装变体，不在正文口头换衣。

### 场景正文

只写**机位、朝向、光位、可走位置、出入口**。不要重写建筑结构、材质、陈设——这些在场景全景图里。重写会造出第二套空间真值，表现是同一场戏的墙、门、窗在镜头间换位置。

**场景参考图是空镜**（0 人 0 车）：人物与车辆若在本镜出现，按绑定行挂 `CHAR_xx`／`PROP_xx`，正文用姓名或资产名点名其在场、位置与动作。不要把「图里已经有的人/车」当成既成事实，也不要求场景图里有人或车。

### 道具正文

只写**状态**：开／合、新／旧、有字／无字、在谁手里。不要重写尺寸、材质、纹样。带字道具另见 [TEXT-01](failure-cases.md#text-01)。

## 四、上传与核对协议

1. **上传顺序固定**：场景 → 角色（按 CHAR 序）→ 道具（按 PROP 序）。顺序只是给人核对用，不写进包。
2. **提交前看清单，只对名字，不对编号**：应用清单里每个资产都能在 `【参考】` 里找到同名项，`【参考】` 里每一项也都在清单里。
3. **清单缺项或多项就停**：不要用编号去"猜"缺的是哪张；缺图先补图，多图先移除。
4. **生成后抽帧核对三锚**：发型、眼镜/饰件、外套品类＋固有色。任一项变化即判错，先查参考图是否被换，再查正文是否重写了服装。
5. **核对应用实际提交的图与用户已审核基准一致**。四视图是同一人的不同视角，不代表多个人；用户已选四视图时保留选择，并检查应用是否错误复制排版/人数。版式本身不能保证不分身，也不能补救漏传人物图。

## 五、换装

同一角色要换第二套衣服，走[服装变体](outfit-variants.md)：另出 `PROP_xx｜角色名·服装名`，图片提示词写「本套装供 CHAR_xx 穿着」，片段 `道具：` 行绑定、`【参考】` 写明由谁穿着。**不允许在正文里口头换衣**（"他脱下外套，露出…" 之后必须绑定变体资产，否则成片会出现第三套）。

## 七、常见误区

| 想法 | 实际 |
|---|---|
| "我按上传顺序写了编号，应该对" | 应用按**本次提交的槽位**重新编号，上传顺序不等于槽位号；预览与出片卡还可能不同 |
| "把编号收进【参考】块就安全了" | 收进去只是好改，错位照旧；必须删掉数字 |
| "编号错位是模型随机" | 不是。错位是可复现的文本缺陷，先对清单，再谈模型 |
| "正文多写点服装细节更保险" | 更危险。文字与图不同源时，模型每镜可能选不同的一套，这才是"换装"的主因 |
| "有四视图就一定不分身、不会漏人" | 仍须检查实际提交图、角色绑定和每镜人数；用户已确认版式优先，不能仅因四视图就要求换掉基准 |
| "写清楚卡只作比对、不作视频参考更保险" | 正好相反：这句话会让应用不把卡当参考，人物全交给文字随机生成（恋爱仅退款 已实证） |
| "给同一套衣服再建一个变体，万无一失" | 同一套衣服登记两次，模型会当成两套来回切；变体只登记真正换掉的那套 |
