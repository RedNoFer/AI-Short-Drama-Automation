# 资产引用绑定规范（唯一真值）

**固定资产代码属于制作包；Wan3.0 轨包内以 `图N=资产代码` 声明映射并在正文用 `名称图N` 绑定，`@ImageN/@图片N` 是应用渲染形态仍不进包；Seedance/H3 轨不预写编号**，H3素材标签按其分支规范映射，不能把资产代码中的数字误判为图片编号。

这份文件管「提示词里的资产怎么被指到正确的图上」，人物、场景、道具一视同仁。导入格式见[精简制作包导入规范](compact-import.md)，资产图本身怎么出见[资产图制作规范](asset-image-production.md)，**资产图与视频提示词各自写什么、不重复什么见[提示词分层规范](prompt-layering.md)**。

## 一、为什么"已经抽离成参考块"仍然全错

2026-10-23 连续在两部片上复现：`三千国道逆己而行-Wan3.0`（5 角色）与 `替身千金`（娜琳／塔纳／护士等）。表现一致——角色拿到别人的脸、场景图被当成人物、道具完全没被引用。

三层原因，缺一层都不会出事，三层叠加就成了系统性错位：

1. **编号是应用的，不是包的。** 应用在提交时按本次上传的图片槽位生成一份**全局**清单：`@图片1：… @图片2：…`。包里的每个片段却各自从 1 开始编号（`@Image1=CHAR_01`），等于每个片段都自造一套序号。两套序号之间没有任何同步机制。
2. **应用清单的顺序不由包决定。** 它可能随上传顺序、拖拽顺序、类型分组变化；同一次提交里，预览框的顺序和实际出片卡上的 `【参考图片】` 顺序都可能不同。包内写死的数字无法预测它。
3. **"抽离"只搬了位置，没有取消数字。** 把散落在正文里的 `@ImageN` 收进一个 `【参考】` 块，确实让改起来更集中，但**写死编号这件事本身没变**。只要包里还有数字，就永远存在"包说一套、应用排一套"的可能。

**结论（2026-11-14 修订）：零编号做法已被实测推翻。**《美元贬值一千万倍》E01-SH01 实证：正文 0 处编号引用时，万相3.0 不把参考图绑定到人物，全员换脸。万相3.0 官方 Prompt 指南明确「两个及以上素材必须写明编号」，官方示例正文一律 `名称图N`。新结论分轨：**Wan3.0 轨包内按固定上传序声明 `图N=资产代码` 映射、正文 `名称图N` 绑定、提交前与应用展开清单双核对（名字＋编号）；Seedance/H3 轨维持不预写编号。** 2026-10-23 两部片的错位根因是"包内序号与应用槽位序无同步机制"——现平台按固定上传序（场景→角色→道具）展开 `@图片N` 清单，顺序可预测，配合提交前核对即闭环。

## 二、引用规则

| 编号 | 规则 | 机检 |
|---|---|---|
| **R1** | Wan3.0 轨 `【参考】` 写 `图N=资产代码` 映射（按固定上传序从 1 连续编号，不写职责描述后缀，不写 `@ImageN/@图片N`）；Seedance/H3 离线包不预写编号；H3使用本分支 `<Subject N>` 等标签，`<Picture N>` 仅指实际上传且已登记的图 | `WAN30-04` 校验映射连续性、分序与正文绑定 |

Wan/Seedance上传槽位编号在应用提交时生成；H3标签遵循其已登记素材映射。下面的四段示例适用于Wan/Seedance，H3仍使用自己的固定字段结构。

## 三、标准写法

### Wan3.0 轨：图N映射＋正文图N绑定

```text
【参考】图1=LOC_01;图2=CHAR_01;图3=CHAR_03;图4=CHAR_04;图5=PROP_01;图6=PROP_05。
```

- **编号按固定上传序**：场景 → 角色（按 CHAR 序）→ 道具（按 PROP 序），从 1 连续编号，与应用展开的 `@图片N` 清单同序。
- **不写职责描述后缀**（`＝身份与默认着装基准（单人塑像图）` 这类括号说明全部删掉）：职责由应用注入的【角色一致性】行与 `@图片N` 清单承载，重复写只会给正文添噪。
- **不写 `@ImageN/@图片N`**：那是应用渲染形态；包内只写 `图N=代码`。
- **正文绑定**：总体描述、空间与入口、场景锚、时间轴画面字段（含镜尾）与收尾中，凡绑定资产主体出现处，称呼后紧跟图N——`Luke图2`、`红色法拉利图5`、`场景图1`（或 `LOC_02图2`）。官方语法即如此（"小女孩图6手举棒棒糖图7"）。
- **全行绑定**：凡绑定资产称呼出现处一律紧跟图N，包括声线锁定、台词/心声说话人标签（`Luke图2(口型对白…)`）、镜头语言、声音纪律、禁止项、镜头段（`在Luke图2侧45°`）。**唯一例外**：画面文字纪律行中泛指的类目词（手机、纸张等，不指具体资产实例）不加编号——E02 顾客的手机不得绑成 Luke 的图6。
- **负向必含**（并入禁止项行）：`全片不要人脸扭曲变形、不要身份漂移、不要服装漂移。`
- 没被本片段用的资产不写进来；正文不会因上传清单多出资产就新增角色。提交前仍须按绑定清单移除无关参考，不能假定多余图片不会影响生成。

### Seedance 等轨：代码＝职责

```text
【参考】
CHAR_01＝身份与默认着装基准（单人塑像图）
CHAR_02＝身份与默认着装基准（单人塑像图）
LOC_01＝空间拓扑与光位基准（全景）
PROP_01＝形制基准（基础态单张）
```

- 一行一个资产，`代码＝职责`，中文分号或换行分隔，句号收尾。**代码后不要再写名称**：应用会把 `CHAR_01` 解析成角色名，写成 `CHAR_01 娜琳＝…` 会渲染成「娜琳 娜琳＝…」，既重复又可能被模型读成两个人。
- 职责只写**这张图负责什么**（身份／服装／空间／光位／形制），不写编号、不写上传位置。

### 人物正文

仅通过听筒或画外发声、在本片段任何镜头都不出镜的角色，保留角色绑定、声源参考职责及声线，不要求画面外观条款，也不为了满足外观校验上传其人像。只要本片段另有实际出镜镜头，就仍按画面角色验收，不能凭某一句“画外”豁免全段。

【参考】已经声明人物身份和本段着装来源，公共层不再复制人物一致性段。状态变化只写必要动作或结果；持久换装绑定服装变体。示例与覆盖范围见[共用质量契约 §2](prompt-quality-contract.md)。

### 场景正文

只写**机位、朝向、光位、可走位置、出入口**。不要重写建筑结构、材质、陈设——这些在场景全景图里。重写会造出第二套空间真值，表现是同一场戏的墙、门、窗在镜头间换位置。

**场景参考图是空镜**（0 人 0 车）：人物与车辆若在本镜出现，按绑定行挂 `CHAR_xx`／`PROP_xx`，正文用姓名或资产名点名其在场、位置与动作。不要把「图里已经有的人/车」当成既成事实，也不要求场景图里有人或车。

### 道具正文

只写**状态**：开／合、新／旧、有字／无字、在谁手里。不要重写尺寸、材质、纹样。带字道具另见 [TEXT-01](failure-cases.md#text-01)。

## 四、上传与核对协议

0. **应用端登记规范**：资产在应用的「项目资产」里登记时，**名称只写纯资产名**（如「红色法拉利」「Luke Lawson」「Grant大厦楼下」），不带括号注记（座驾归属、集号、时段、基准职责等）；**描述/备注字段留空**。括号注记只存在于制作包资产卡标题（内部文档用途）。应用端登记带了注记，会随每次提交的 `@图片N` 清单持续渲染进提示词（2026-11-14 实证）；清理只能在应用端做，包内已管不到。
1. **上传顺序固定**：场景 → 角色（按 CHAR 序）→ 道具（按 PROP 序）。包内 `图N=代码` 映射即按此序编号。
2. **提交前看清单，名字与编号都对**：应用展开的 `@图片N` 清单里每一项的类型、名称、编号都必须与本卡 `图N=代码` 映射一致；名字对上而编号错位同样会串脸。
3. **清单缺项或多项就停**：不要用编号去"猜"缺的是哪张；缺图先补图，多图先移除。
4. **生成后抽帧核对角色与资产图**：发型、眼镜/饰件、外套品类＋固有色。任一项变化即判错，先查参考图是否被换，再查正文是否重写了服装。
5. **核对应用实际提交的图与用户已审核基准一致**。四视图是同一人的不同视角，不代表多个人；用户已选四视图时保留选择，并检查应用是否错误复制排版/人数。版式本身不能保证不分身，也不能补救漏传人物图。

## 五、换装

**强制先解析本段服装来源**：按[OUTFIT-04](outfit-variants.md#片段级着装来源解析outfit-04必须执行)切开身份与着装职责，公共层补 `着装来源：CHAR_xx＝PROP_xx（替换默认着装）`；局部覆盖写具体部位，其余沿用默认装。不得让人物图与服装资产同时声明服装唯一基准。

同一角色要换第二套衣服，走[服装变体](outfit-variants.md)：另出 `PROP_xx｜角色名·服装名`，图片提示词写「本套装供 CHAR_xx 穿着」，片段 `道具：` 行绑定、`【参考】` 写明由谁穿着。**不允许在正文里口头换衣**（"他脱下外套，露出…" 之后必须绑定变体资产，否则成片会出现第三套）。

## 七、常见误区

| 想法 | 实际 |
|---|---|
| "正文用姓名就够了，模型自己会对上图" | 不会。万相3.0 官方要求两个及以上素材必须写编号引用，正文 0 处图N＝全员随机脸（美元贬值 E01-SH01 已实证） |
| "我按上传顺序写了编号，应该对" | 上传顺序固定为场景→角色→道具时槽位号可预测；但提交前仍须与应用展开的 `@图片N` 清单双核对（名字＋编号），顺序变化就停 |
| "把编号收进【参考】块、正文只写名字就安全了" | 声明块只告诉应用有哪些图；模型绑定靠**正文**图N。正文不写编号＝声明块形同虚设 |
| "编号错位是模型随机" | 不是。错位是可复现的文本缺陷，先对清单，再谈模型 |
| "正文多写点服装细节更保险" | 更危险。文字与图不同源时，模型每镜可能选不同的一套，这才是"换装"的主因 |
| "正文多写点服装细节更保险" | 更危险。文字与图不同源时，模型每镜可能选不同的一套，这才是"换装"的主因 |
| "有四视图就一定不分身、不会漏人" | 仍须检查实际提交图、角色绑定和每镜人数；用户已确认版式优先，不能仅因四视图就要求换掉基准 |
| "写清楚卡只作比对、不作视频参考更保险" | 正好相反：这句话会让应用不把卡当参考，人物全交给文字随机生成（恋爱仅退款 已实证） |
| "给同一套衣服再建一个变体，万无一失" | 同一套衣服登记两次，模型会当成两套来回切；变体只登记真正换掉的那套 |
