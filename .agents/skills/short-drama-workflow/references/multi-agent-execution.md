# 多智能体隔离执行规范

本工作流默认以「一个总控 + 多个阶段执行员 + 独立评审员」的方式运行。目的不是多花钱，而是让每个 agent 的上下文只装当前阶段必需的材料，从机制上消灭 PROC-01（装不下就跳读）和「起草人自审」两类事故；阶段产物全部落盘交接，最后统一走机检与评审验收。

## 角色分工

| 角色 | 谁来当 | 持有什么 | 不做什么 |
|---|---|---|---|
| 总控（编排者） | 主会话 | 项目输入单、阶段检查单、执行账、本规范、[规则传播登记表](rule-map.md) | 不亲自写剧本/资产/分镜/提示词正文；不代替评审下结论 |
| 阶段执行员 | 每个阶段（或每集批次）一个**全新子任务** | 交接包：本阶段必读文件路径 + 上阶段产物路径 + 本阶段闸口条件 | 不读后续阶段文件；不自行扩大必读范围；不直接宣布「评审通过」 |
| 独立评审员 | 另一个**全新子任务**，与执行员上下文隔离 | 交接包 + 被审产物 + 对照依据路径 | 不改文件（只出评审记录与缺陷清单）；修复由执行员做 |
| 机检 | 脚本 | policy.json 与制作包 | 不做语义判断 |

无法派发子任务的环境（如纯单会话工具）：允许同一 agent 串行执行，但必须模拟隔离——严格按检查单限定当前阶段读取范围，执行与评审分两个全新上下文窗口进行，并在执行账注明「单会话降级执行」。

## 上下文纪律（硬约束）

1. 交接包给**路径**，不转贴全文；执行员只读清单内文件。清单外问题回报总控裁决，不得自行翻读后续阶段规范。
2. 执行员产出只写入交接包指定的内部档案与制作包位置，不改动其他阶段产物。
3. 上阶段产物是本阶段唯一输入事实；发现上游矛盾时挂起并回报，不在本阶段偷偷修正。
4. 每个执行员返回固定格式的阶段报告（见下），总控核验证据路径后才放行下一阶段。
5. 评审员与执行员不得复用同一子任务；评审员可以换不同模型（可选增强），但至少是全新独立上下文。
6. **总控下发的每个事实约束都必须附「依据原句」**（正文/剧本/资产卡里能逐字查到的那一句，注明出处集/片段/镜头或章节）。给不出原句的约束，视为总控臆断，不得下派。
7. **执行员有质疑权，也有质疑义务**：发现交接包里的约束与所读正文矛盾时，**必须先停下、引用原句回报总控**，不得照单执行、也不得自行静默修正。本轮（2026-10-22）的总控座次表写反，正是执行员靠这条抓出来的——照单全收就会把错误带进成片。
8. **阶段出口门是放行条件**：阶段报告必须附 `validate_stage_artifacts.py --stage N`（N＝2｜3｜3.5｜4）的实际输出；总控见「0 错误」才签放行。执行员不得以「下游更急」为由要求跳过门。门查结构（标题下有正文、表格有数据行、视感统计与逐镜表一致），**用空壳文档骗门与跳步同级处理**。
9. **评审不得复用执行员的结论**：阶段 2 的资产评审与阶段 4 的一轮全覆盖评审都必须由新子任务承担；执行员把「我已自检」写进报告不等于评审完成，缺评审记录时阶段出口门直接判错。

## 批次版本锁与并行验收

每批派单必须带一个可追溯版本锁，避免并行稿读到不同剧情/资产/分镜，或评审通过后又被覆盖。提示词评审逐条记录最终包中的片段 ID 与提示词正文哈希，便于机检确认覆盖和只重审发生变化的提示词。哈希统一对 `#### 视频提示词` 的 `text` 块原文计算：

1. 总控先冻结本阶段上游产物（阶段4必须含已与分镜核对通过的 `04c-衔接事实.json`），并在派单写明批次 ID、唯一模型轨及策略档、上游文件 SHA-256、边界片段、可写文件和验收命令。
2. 每个执行员只写自己的隔离文件；不得让多个执行员同时改主剧本、主分镜表、同一份制作包或共享母版。
3. 执行员报告输出路径与 SHA-256。阶段 3 独立评审记录被评分镜稿的同一哈希；阶段 4 全覆盖评审逐行记录最终包中每条视频提示词正文的 SHA-256。阶段 3 草稿文件变化会使批次结论失效；阶段 4 以提示词正文哈希为准，正文变化即定向复验。
4. 阶段 3 总控仅合并哈希与独立评审一致的批次，合并后运行一次全局交叉检查和阶段出口门。阶段 4 批次本地 lint/机械检查硬错为零后即可合并到符合固定模板的唯一 `精简制作包.md` 待评稿，仍保持「待评」；整套机械硬错与原文覆盖率通过后，再进行唯一一轮全覆盖语义评审；Wan风险提醒在本轮按[处置契约](prompt-review.md#wan风险提醒处置)留证，最终严格门要求全部有效处置。如合并产生冲突，只退回受影响批次，不重写已通过的无关批次。
5. 任何上游冻结版本变化，都列出受影响下游批次并使其验收失效；没有依赖关系的批次继续并行。

### 派单与台账由脚本生成（2026-10-25）

Wan3.0 派单与manifest由当前policy派生：仅18000字符硬上限，`min_chars`为`null`；不生成目标字数、单拍字数或章节占比任务。逐镜详细程度按[Wan内容验收](wan30-prompt-spec.md#逐镜内容验收)检查。长度策略变更后，恢复存量批次时同步输入单并重新生成卡与manifest；不手改旧快照或自动刷新旧评审结论。

派单卡里那一堆数值（唯一模型轨、字符档、硬切带、上游哈希、校验命令）**不再由总控抄写**：

- `scripts/build_handoff.py <作品目录> --stage 3|4 --batch <范围> --out <卡> --manifest-out <manifest>` 从输入单与 `policy.json` 构造卡，并同时产出机器可读的批次清单。阶段 3/4 派单会核对上游阶段门收据与评审状态；缺失、未通过或哈希过期时**失败关闭**。每个上游出口门只在阶段完成时运行一次，多个下游批次复用仍有效的收据。
- `scripts/batch_ledger.py <作品目录> sync` 把 `内部/派单/*.manifest.json` 收进 `内部/批次台账.json`；`set --batch-id … --state 通过 --draft … --review … --gate "0 错误"` 改状态；`status` 打印全部批次与问题。批次 ID 含阶段号，防止同一片段的阶段 3/4 记录互相覆盖。
- 台账替总控盯三件事：**草稿与评审版本锁**（草稿改动会清除旧评审；阶段 4 分节报告只锁本批片段分节及共享约束，其他片段变更不作废本批；旧平铺报告仍锁整文件；标通过必须有明确且唯一的 `0 错误` 门结果）、**上游失效**（资产/共享母版变化退回依赖批次；逐镜表按本批片段哈希定位，其他片段变化不作废本批）、**规范漂移**（manifest 的 policy 版本落后 → 提醒，是否重跑按改动范围定）。
- 总控汇报进度时以 `status` 输出为准，不凭记忆：「这批评过了」必须能在台账里查到同一哈希的评审记录。

### 阶段 4 评审报告与范围版本锁

- 实际评审报告以 `## 片段 E01-SH01` 为每段分节，放本段证据与唯一一张「当前验收表」；表头为 `片段ID | 正文SHA-256 | 结论`，每段只保留一条当前数据行，结论只有明确的 `通过` 才放行。哈希对当前包 `#### 视频提示词` 的 `text` 块原文计算。全集每段必须且只能出现一条当前验收记录；重复、冲突、待评或需修改均阻断。历史缺陷与修复经过写叙述或无哈希的历史记录，不复制当前验收表。
- 评审人、模型分支、冻结上游及跨片段共同约束置于片段分节之外，属于共享依赖。报告末用 `## 全局汇总` 记录总评 `结论：通过/需修改` 和 `未关闭阻断/重要缺陷：N`；阶段 4 全局门检查它们。仅汇总数字或总评状态变化不触发全部片段重新语义评审；有未关闭缺陷仍会阻断阶段放行。
- 台账对分节报告锁本批各片段分节与共享约束内容；其他片段的评审变更不使本批失效，共享依赖或评审人变化仍使依赖批次失效。旧平铺报告继续按整文件锁处理，不自动转换成分节报告，也不补造通过结论。
- 每批 `--review` 必须指向包含该批实际证据和当前验收记录的评审报告，不可指向只有链接的索引。`05-评审索引.md` 仅汇总实际报告名、范围和覆盖关系；只有列入索引的实际报告参与全局验收。报告的具体写法见[交接模板](handoff-template.md#阶段-4-全套提示词独立评审全部草稿完成后)。


### 派单依赖完整性

manifest 是执行员的读取白名单，不负责替总控判断任务应走哪个路由。总控先按根目录 `AGENTS.md` 和影视工作流导航选定主流程、分支及触发的专项规范，再确认派单卡与 manifest 已列出完成本批所需的 Skill、policy／适配器、阶段参考、上游材料及验收依据。`build_handoff.py` 检查阶段证据和版本锁；语义结论仍由隔离评审员作出，文件存在或机械门通过都不能替代评审。

若必需文件缺失、路径失效或约束相互冲突，该批派单无效：执行员停止写作并报告总控；总控修正输入或生成规则后，重新生成卡与 manifest。执行员不得自行扩大读取范围，也不应要求用户裁决内部派单缺项。

**验收顺序按阶段区分**：阶段 3 分镜按批次做本地检查与独立评审，全部批次通过后合并并跑一次全局阶段门。阶段 4 提示词写作期间逐段自查并运行 `lint_segment.py`；全集完成后先跑登记轨的包校验与原文覆盖率，机械硬错清零后做**一轮全覆盖独立评审**，评审可按互不重叠的片段范围分派给多人；分拆报告数量不限，索引须逐文件列出实际报告名，各范围不重叠且覆盖全集，未列入索引的旧稿不参与验收。不先做一轮批次独立评审、再重复做一次全文独立评审。阶段 5 对最终包复跑机械校验与覆盖检查。任何门未通过时都按缺陷定位回退到受影响单元，不重审无关的通过内容。

### 快速并行执行卡（默认）

1. **先锁定阶段输入，再按边界并行**：总控先确认上游放行证据和唯一模型轨。阶段 3/4 作者批次按轨建议：Wan3.0 每批 1–2 段，Seedance 2.5/H3 每批 2–4 段（`policy.json` 的 `execution.batch_size_by_track`）；总控按预计文字量、对白密度、道具链和空间风险调整。此为派单建议，不改变片段时长或字符目标，不拆用户锁定片段，也不把一个片段拆给多个作者。最多同时派发可用执行槽数减一的批次，总控保留一个槽做合并与门控。
2. **一批一张短卡**：只列批次 ID、唯一轨及本轨长度策略（阶段4）、本批片段范围、必要上游文件路径与 SHA-256、可写路径、本地校验命令和通过条件。阶段 3 批次卡列独立评审人；阶段 4 草稿卡列作者与 lint/机检命令，独立评审在整套提示词完成后统一派发。不要把全局规则全文复制进派单；用精确文件＋章节锚点，只加载命中的分支与风险规则。
3. **按阶段验收，不重复评审**：阶段 3 执行员落盘后跑本批确定性检查并由独立评审员复核，同一 SHA-256 的两项通过后标记批次通过；全部批次合并后跑一次全局交叉检查和出口门。阶段 4 写作期间由作者逐段自查、运行 lint 和必要的分支机检，批次状态保持「待评」；本地检查通过即可并入符合固定模板的唯一 `精简制作包.md` 待评稿。全部提示词合并后先跑一次整套机械校验与原文覆盖率，再由多名隔离评审员按不重叠范围并行完成同一轮全覆盖评审。评审通过后将对应阶段4批次登记为「通过」并绑定全覆盖报告；阶段4出口门同时核对本批评审范围版本锁、批次状态、局部 0 错误结果和上游版本是否仍有效。不能每批重跑全项目门，也不能把本地机检不通过的批次合并进汇总稿。
4. **阶段 4 评审分工去重**：完整提示词集就绪后，可把互不重叠的片段范围分给多个隔离评审员，组成同一轮全覆盖评审；总控负责跨范围连续性、共享资产/分支一致性和总体覆盖。修复复验只覆盖变更条目、相邻接口及受影响的全局项，不重读哈希未变且已有有效结论的全文。
5. **单一缺陷回退单元**：全局门报错时，按报告定位唯一受影响批次/文件，只修该处及其相邻依赖；复跑该批检查、相邻回归和一次全局门。未受影响且哈希未变的通过批次保持有效。

**批次状态只有四种**：`待写`、`待评`、`退修`、`通过`。阶段放行条件是所有批次 `通过` 且该阶段全局门为 0 错误；执行账只记录批次汇总、哈希、全局门命令/结果和阻断数，详细逐条证据留在批次评审文件。

## 交接包模板（总控 → 执行员）

```text
【阶段】编号与名称
【范围】负责的集/片段/资产清单
【必读】skill 文件与源文件的绝对路径（白名单，读完即止）
【上游输入】上阶段落盘产物路径 + 入口事实摘要（不贴全文）
【产出】要写入/更新的文件绝对路径
【依据原句】每条事实约束对应的正文/剧本原句（逐字，注明出处）；给不出原句的约束不得下派
【闸口】机检命令与语义通过条件（引自阶段检查单），含阶段出口门 `validate_stage_artifacts.py --stage N`
【禁止】不得读取的后续阶段文件、不得做的决定
【返回】阶段报告：结论(通过/挂起/失败)、证据路径、未决问题、字符/数量统计
```

评审交接包额外给：被审产物路径、对照依据（小说源文件、内部剧本/分镜、规范）、五个对抗视角、缺陷记录模板。

| 3 片段与分镜 | 按集/片段批次派执行员；各自只读本集剧本、母版和相邻边界事实，输出到独立草稿 | 不同集或不重叠片段并行；共享主表只由总控合并 | 每批先跑视感/空间/台词与局部衔接检查并独立复核；合并后一次全局交叉校验和出口门 `--stage 3` 必须为 0 错误。打斗路由随分镜批次同步登记与复核；阶段 3、3.5 门均通过后才可开阶段 4 |
| 3.5 打斗路由 | 阶段 3 执行员按路由表登记；独立评审员在同一分镜评审包中核对命中段的等级、证据与拍点，不另起重复评审任务 | 与阶段 3 批次评审合并处理 | 判定表落盘、A 级带拍点与证据、独立复核完成、出口门 `--stage 3.5` 为 0 错误；全剧无打斗明确登记全 C |
| 4 最终提示词 | 仅在阶段 0–3.5 的上游评审、出口门与版本锁全部通过后启动；按集/片段批次写入隔离草稿 | 作者可按不重叠片段并行；独立评审在全部提示词完成后做一轮全覆盖，可由多名评审员分担互不重叠范围 | 每条即时自查并运行 `lint_segment.py`；模型分支格式/字符策略按登记轨；完成后由独立评审一次性覆盖所有提示词并检查跨片接口，结论落 `05`。问题关闭且阶段 4 门通过后才进入阶段 5 |
| 5 导出与机检 | 总控导出唯一制作包、运行分支校验器、原文覆盖率与工作流清单门 | 导出与机械检查可由总控串行完成 | 机检 rc=0、覆盖率达标、评审缺陷全关闭、执行账齐全；不再重复做上游或提示词语义评审 |
| 6 视频遵循 | 实际生成后按批派评审员 | 各批并行 | 逐片证据记录 |

并行的硬边界：共享母版（视觉、声线、资产 ID）未冻结前不得并行；并行批次之间的出入口事实由总控在派单时写死，执行员不得自行协商改边界。

## 回滚与复验（同 [提示词质量规范](prompt-review.md)）

- 总控维护最近一次通过版本与上游冻结哈希，评审结论关联具体文件及提示词片段哈希。
- 提示词评审判阻断/重要：先判定缺陷来源。提示词表达或编译错误由执行员只修相关提示词；若证据表明上游产物自身有误，将其登记为上游验收漏项，只重开最早出错产物及依赖该产物的下游单元，不重启阶段 0–4 全流程。
- 修复后评审员做**一次定向修复复验**：未变提示词凭哈希与原结论确认；变更提示词、相邻接口及受影响共享项重审；全局交叉项只重查受影响部分。该复验不要求重读所有未变提示词，也不重新评一遍剧情、资产和分镜。
- 同一缺陷两次复验不过：停止沿用原方法重复返工，由总控定位根因并更换修复方法；只有需要改变用户锁定目标或缺少必要用户决策时，才带具体候选方案询问用户。

## 速度纪律

隔离执行不等于多跑流程：能给路径不给全文；阶段 1–3.5 在各自交接点验收，阶段 4 写作期间做段内自查和机检，全部提示词完成后进行一轮独立全覆盖评审，阶段 5 运行最终包机检。不得把上游缺陷留给提示词评审，也不得在阶段 5 重复进行提示词语义评审。任何「为了快而合并阶段、跳过必读、让起草人代替独立评审」的做法都属流程违规，登记 PROC-01。

Wan警告不等于硬错误：作者lint只阻断硬错并报告未验风险；全集独立评审按[风险处置契约](prompt-review.md#wan风险提醒处置)关闭warning，阶段4严格门验证记录。连续性事实在阶段3先验收冻结，阶段4对正文交叉验；原语估时按[声线与配音规范](voice-and-dubbing.md)核对，不把中文翻译或动作时间机械叠加到发声时间。
